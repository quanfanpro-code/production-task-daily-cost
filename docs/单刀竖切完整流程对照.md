# 单刀竖切：完整流程对照

> 历史试验记录。文中拼接、本地识别补具体字段、交接和当时未提交等描述不代表当前流程；本地误读不能作为专业漏读的依据。当前规则和最新实测以[使用说明](../readme.md)为准。

日期：2026年10月15日。未提交、未推送。

## 改了什么

已彻底移除拼图、逐列拆图和重排。每页只竖切一刀，从原页左边保留到最右必要字段；上下整页高度、文字大小和所有内部相对位置保持不变。每个有效页只有一个裁剪框、一张图片，PNG无损保存；13张输出逐像素验证等于原页对应区域。原页和旧缓存不删除。工序名、日期之间必要的原表内容保留，不为了缩小面积再次挖掉中间列。

图纸三页仍不进入识别。计划与旧式竖版记录的日期靠右时，切口相应靠右，宁可保留较宽原区域，不重排或拆成多张。找不到必要列时保留原页。执行仍调用原有准备、专业识别、日期推算和写表程序。

## 比较条件

相同原件16页，复用同一份转正和本地粗识别缓存，排除3页图纸，4份任务。裸跑用完整原页直接取数；新流程每个有效页一张整块裁图，交GLM-OCR识别，通用模型只处理文字。两组使用同一执行模型gpt-6.1-sol及相同推理设置，均复用同一日期推算和工作簿生成程序，没有重写算法。

复用已有两个对照执行者，各接续运行一次，没有新增代理或全量复核。这是同例接续回归，各自带有上轮上下文，不能当作独立盲测或新批次保证。没有给执行者评判答案，没有根据分数重跑或改写结果。新裁图与旧拼图内容不同，因此13张新输入各识别一次；既有本地OCR没有重做，旧专业缓存保留。

仅将裁剪、OCR和文字整理相加是166.568秒，但漏掉了约34.6秒交接，不能拿它声称比裸跑更快。交接是本轮实际对照控制端的等待，不据此断言专业OCR自身变慢。完整时间起点的专业请求记录精确到秒，因此总时间标“约”，不伪造毫秒精度。

用量计入执行者本轮从读输入、取数、推断到生成表格的全部轮次，并加入专业OCR实际返回用量；推理输出已包含在输出中，不重复相加。开发、对照控制和评判对话另属开发评测开销，不混入这张处理用量表。共同已经完成的转正和本地粗识别没有重算；本地裁剪后为了安排裸跑对照而排队的测试等待不冒充生产流程耗时。

## 日期质量

| 核对内容 | 裸跑 | 新流程 |
| --- | ---: | ---: |
| 预先选定15个原日期对应 | 14/15 | 15/15 |
| 两个明确区间日期集合 | 2/2 | 2/2 |
| 一份任务4个完整工序日期集合 | 3/4 | 4/4 |
| 任务数、正常逐日行数 | 4份、53行 | 4份、53行 |

工序名先按已有程序的别名规则统一，避免把“研磨/精磨”名称差异误计成日期错误。裸跑仍将用户确认的9.4读成9.6；新流程对应9.4。第7页1.4、3.11等出现在第一次整块识别中，没有事后拆图补读。第10页0.3结合整任务推为9月3日，这属于推断，不能算原OCR直接读对。

不能据此宣称整体日期质量更好：两份表只有43行日期键一致，各有10行不同。新流程未取到第7页4月中旬那条双轴加工日期，并把已识别的双轴4.16/4.17、环抛3.30/3.31处理日期仅作备注，遗漏了可能应计入的返修。双轴1月涂改结束日采用1.9，裸跑采用1.6；环抛1月双方读数也不同。第14页新流程把4.6推为5.6，仍保留5.9节点，裸跑采用4.30至5.5相关时点。新流程未触发额外OCR请求，也未为对齐旧答案更改数据。

这些差异混合了专业OCR漏读、估读差异和记录归类差异；53行相等不代表内容一致，15个选定日期全对应也不是全文件准确率100%。本轮证明拼接已移除且选定日期覆盖改善，仍不能确认全量精度达标。
